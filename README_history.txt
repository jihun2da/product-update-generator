카페24 자동 업로드 기능 — 상세 오류 수정/개발 이력
====================================================

이 파일은 README.txt의 "카페24 자동 업로드" 절에 있던 날짜별 상세 디버깅 기록을
그대로 보관한 원본입니다. 각 항목은 당시 겪었던 증상, 원인 분석 과정, 수정 내용,
로컬 테스트로 검증한 내용을 시간 순서대로 담고 있습니다. 최종 결론과 현재 동작
방식은 README.txt의 "카페24 자동 업로드 — 변경 이력(요약)" 부분을 참고하세요.

⚠️ 오류 수정 (2026-08-26) — "성공으로 나왔는데 실제로는 아무것도 업로드되지 않음"
문제: 업로드 화면에서 "전용 엑셀양식 다운로드" 같은 안내 팝업이 새로 뜨면서 업로드
버튼을 가려, 실제로는 버튼 클릭 자체가 막혔는데도 이를 조용히 넘어가서 "성공"으로
잘못 표시되는 문제가 있었습니다. 이제는:
  - 업로드 화면 진입 직후, 파일 첨부 후 등 여러 시점에서 팝업을 자동으로 정리하도록
    강화했고,
  - 그래도 업로드 버튼 클릭이 끝내 막히면(팝업이 안 닫히는 경우 등) 더 이상 "성공"으로
    처리하지 않고, 화면에 남아있던 팝업 내용을 메시지에 담아 "오류"로 명확히
    보고합니다.
로컬 테스트 페이지로 "팝업이 버튼을 가리는 상황 → 자동으로 닫고 재시도 → 성공",
"팝업이 안 닫히는 상황 → 오류로 보고(성공으로 잘못 표시 안 됨)", "팝업이 아예 없는
정상 상황 → 그대로 성공" 세 가지 시나리오를 재현해서 검증했습니다. 다만 클라우드
환경은 headless(화면 없이) 실행이라 진행 과정을 직접 눈으로 볼 수는 없고, 계정별
스크린샷으로만 확인할 수 있습니다 — 실행 과정을 직접 눈으로 보고 싶으시면, 이 앱을
본인 컴퓨터에 내려받아 `streamlit run app.py`로 로컬 실행한 뒤 "③"의 headless 체크를
해제하고 실행하시면 브라우저 창이 실제로 뜨는 걸 볼 수 있습니다(Streamlit Cloud에는
화면이 없어서 이 옵션이 동작하지 않습니다).

⚠️ 오류 수정 (2026-08-26) — 로컬(Windows)에서 실행 시 "NotImplementedError" 발생
문제: 로컬 Windows PC에서 `streamlit run app.py`로 실행 중 업로드를 시작하면
"NotImplementedError" (…asyncio/base_events.py, _make_subprocess_transport…) 오류가
발생하며 Chromium 자체가 실행되지 못하는 문제가 있었습니다. 원인은 Streamlit이 내부적으로
사용하는 웹서버(Tornado)가 Windows에서 자식 프로세스 실행을 지원하지 않는 이벤트 루프
정책(WindowsSelectorEventLoopPolicy)을 설정해두기 때문으로, Playwright가 Chromium을
자식 프로세스로 띄우려 할 때 이 제약에 걸립니다. 이제 업로드 시작 직전에 자식 프로세스
실행을 지원하는 정책(WindowsProactorEventLoopPolicy)으로 자동 전환하도록 수정했습니다.
Windows가 아닌 환경(Streamlit Cloud 등 리눅스 서버)에서는 이 로직이 아무 동작도 하지
않도록(no-op) 만들어, 기존 클라우드 동작에는 영향이 없습니다.

🆕 기능 추가 (2026-08-26) — 디버그: 업로드 화면 진입 직후 자동 진행 멈추기
"③ 업로드 실행"에 체크박스를 하나 추가했습니다. "브라우저 화면 없이 실행(headless)"을
해제한 상태(로컬 실행)에서만 사용할 수 있고, 체크하면 업로드 화면(엑셀 업로드 페이지)에
막 들어간 직후 — 자동 팝업 정리나 파일 첨부를 하기 전 — 자동화가 멈추고 Playwright
인스펙터 창이 뜹니다. 이 상태에서 실제 카페24 화면에 뜬 팝업이나 버튼을 개발자도구(F12)
또는 인스펙터로 직접 검사해서 정확한 선택자(class/id/xpath)를 확인할 수 있고, 다 확인한
뒤 인스펙터의 '재생(▶ Resume)' 버튼을 누르면 이어서 진행됩니다. headless 상태에서는
볼 화면이 없어 무한 대기하게 되므로 자동으로 비활성화(사용 불가)됩니다.

✅ 팝업 선택자 확정 (2026-08-27) — "상품등록용 엑셀 다운로드" 안내 팝업
위 디버그 모드로 사용자가 직접 화면을 확인해서, 업로드 화면에 처음 진입할 때 뜨는
"상품등록용 엑셀 다운로드" 안내(Step1/3 등 walkthrough 형태) 팝업의 닫기(×) 버튼 정확한
경로를 확인해주셨습니다. 이 선택자를 자동 팝업 정리 로직에서 가장 먼저 시도하도록
추가했습니다. 로컬 테스트 페이지로 해당 구조를 재현해서 팝업이 정상적으로 닫히고, 닫힌
뒤 업로드 버튼 클릭도 정상 동작하는 것을 확인했고, 기존 "확인" 버튼 팝업 시나리오도 함께
재검증해 회귀가 없음을 확인했습니다.

⚠️ 오류 수정 (2026-08-27) — 위 선택자가 실제로는 안 닫히던 문제
위에서 확정했던 경로(`div[2]/div[1]/div[1]/div/button`)로 실제 업로드를 실행해보니
닫기 버튼이 눌리지 않고 오류로 처리되는 것이 확인됐습니다. 사용자가 디버그 모드로 다시
확인해서 정확한 경로가 `//*[@id="QA_upload2"]/div[2]/div[2]/div[1]/div/button`
(두 번째 단계가 div[1]이 아니라 div[2])인 것으로 재확인해주셨고, 이 경로로 수정했습니다.
수정 전 경로가 실제로는 팝업을 못 찾는다는 것과, 수정 후 경로로는 팝업이 정상적으로
닫히고 이어서 업로드 버튼 클릭까지 성공한다는 것을 로컬 테스트 페이지로 재현해 확인했고,
기존 "확인" 버튼 팝업 / 팝업 없음 / 안 닫히는 팝업(오류 처리) 3가지 시나리오도 모두 다시
돌려 회귀가 없음을 확인했습니다.

⚠️ 오류 수정 (2026-08-27) — 팝업은 닫히는데 업로드는 진행되지 않고 창이 바로 닫히던 문제
안내 팝업이 정상적으로 닫힌 뒤에도, 파일을 첨부하고 업로드 버튼을 누르면 카페24가
"해당 파일을 업로드 하시겠습니까?" 같은 브라우저 네이티브 확인창을 띄우는 것이
확인됐습니다. Playwright는 이런 확인창을 처리하는 코드가 없으면 기본적으로 자동
"취소" 처리를 해버리는데, 지금까지는 이 확인창을 전혀 다루지 않고 있어서 업로드가
조용히 취소되고 그대로 계정 처리가 끝나(화면도 바로 닫힘) 버리고 있었습니다. 이제
페이지가 열리는 시점부터 이런 확인창이 뜨면 항상 자동으로 "확인"을 누른 것과 동일하게
처리하도록 수정했습니다. 확인창에 뜬 문구도 함께 기록해서, 실패 문구 판별이나 결과
메시지에 참고용으로 표시됩니다. 실제 confirm() 확인창을 재현한 로컬 테스트로 (1) 기존
방식은 자동 취소된다는 것, (2) 수정 후에는 자동 승인된다는 것, (3) 팝업 닫기 → 업로드
버튼 클릭 → 확인창 자동 승인까지 이어지는 전체 흐름이 정상 동작한다는 것을 확인했고,
기존 팝업 관련 시나리오들도 모두 다시 돌려 회귀가 없음을 확인했습니다. 업로드 버튼
클릭 후 대기 시간(기본 3초)은 기존 옵션이 그대로 적용됩니다.

⚠️ 오류 수정 (2026-08-27) — Windows 로컬 실행 시 "[Errno 2] No such file or
directory: '/tmp/_cafe24_upload_...xlsx'" 오류
파일을 임시로 저장할 때 경로를 "/tmp/..."로 하드코딩해뒀는데, 이 경로는 리눅스(Streamlit
Cloud)에는 항상 있지만 Windows에는 존재하지 않아 로컬 실행 시 파일을 못 찾는 오류가
났습니다. 이제 OS에 맞는 임시 폴더를 자동으로 찾아주는 표준 방법(tempfile)을 쓰도록
수정해서, Windows에서는 Windows의 임시 폴더를, 클라우드(리눅스)에서는 기존과 동일하게
/tmp를 사용합니다. 계정 이름에 예상치 못한 문자가 섞여 있어도 파일 경로가 깨지지 않도록
안전 처리도 함께 추가했습니다. 임시 파일 쓰기/읽기/삭제와 기존 팝업·확인창 처리 흐름을
모두 다시 로컬 테스트로 재검증해 회귀가 없음을 확인했습니다.

⚠️ 오류 수정 (2026-08-27) — 업로드 버튼을 누른 뒤 서버 처리가 끝나기 전에 창을 닫아
"진행중 100%"인 채로 실제로는 아무것도 반영되지 않던 문제
업로드 버튼을 누르고(확인창까지 자동 승인한) 뒤, 실제 카페24 서버 처리가 끝나기 전에
정해진 대기 시간(기존 기본 3초)만 채우고 바로 브라우저를 닫아버리는 경우가 있었습니다.
상품 수가 많은 파일일수록 서버 처리 시간이 길어지는데, 화면에는 파일이 "진행중 100%"로
붙어 있는 것처럼 보이지만 실제로는 아직 처리 중이었고, 그 상태에서 브라우저가 닫히며
아무것도 반영되지 않는 채로 "성공"으로 잘못 표시됐습니다. 이제 고정 대기 전에 먼저
네트워크 활동이 실제로 잠잠해질 때까지(진행 중이던 업로드 요청이 진짜로 끝날 때까지,
최대 60초) 기다리도록 수정했고, 그 뒤에 기존 대기 시간(기본값을 3초에서 5초로 상향)을
추가로 적용합니다. 상품 수가 아주 많아 그래도 오래 걸리는 경우를 위해 "③"의 대기 시간
값을 늘릴 수 있다는 안내도 화면에 추가했습니다. 실제 느린 서버 응답(2.5초 지연)을
재현한 로컬 테스트로 이 대기 로직이 정말로 처리가 끝날 때까지 기다려준다는 것과, 계속
네트워크 활동이 있는 극단적 상황에서도 최대 대기 시간 안에서 안전하게 빠져나온다는 것을
확인했고, 기존 팝업·확인창 처리 흐름도 모두 다시 검증해 회귀가 없음을 확인했습니다.

⚠️ 오류 수정 (2026-08-27) — 대기 시간을 늘렸는데도 여전히 업로드 버튼이 눌리지 않던
문제 (파일 첨부 직후 클릭 타이밍 문제)
바로 앞의 수정(서버 처리 완료까지 대기)을 적용한 뒤에도 여전히 파일만 "진행중 100%"로
붙고 실제 업로드 이력에는 반영되지 않는 문제가 재현됐습니다. 원인을 다시 확인해보니,
파일을 방금 첨부한 직후에는 화면이 파일을 검증/미리보기 처리하는 중이라 업로드
버튼(`#dropZone`의 버튼, xpath: `//*[@id="dropZone"]/div/div[2]/button`)이 아직
"파일찾기"(파일 선택) 상태에서 "업로드"(업로드 시작) 상태로 완전히 바뀌지 않은 순간이
있었습니다. 이 상태에서 곧바로 버튼을 누르면 클릭 자체는 예외 없이 "성공"하지만,
실제로는 파일 선택창을 다시 여는 것과 같은 동작만 하고 서버 업로드는 전혀 시작되지
않았던 것입니다 — 화면에는 파일이 100%로 붙어있는 것처럼 보이는데 실제 업로드 이력에는
아무것도 안 남는 지금까지의 증상과 정확히 일치합니다. 이제 파일 첨부 직후, 버튼을
누르기 전에 먼저 (1) 파일 검증 관련 네트워크 활동이 잠잠해질 때까지 기다리고(최대 8초)
(2) 화면이 완전히 전환될 여유로 추가 대기(1.5초)를 하도록 수정했습니다. 진단을 더
쉽게 하기 위해, 업로드 버튼을 누르기 직전 / 누른 직후 화면 스크린샷도 추가로 저장해서
"④ 업로드 결과 → 계정별 스크린샷 보기"에서 최종 화면과 함께 3장을 나란히 비교할 수
있도록 했습니다(클릭 전/후 화면이 똑같아 보인다면 클릭이 실제로 아무 동작도 하지
않았다는 뜻이므로 추가 진단에 활용할 수 있습니다). 로컬 테스트 서버로 "파일 검증이
끝나기 전에 클릭하면 잘못된 동작이 재현되고, 대기 후 클릭하면 정상 동작한다"는 것을
직접 확인했고, 로그인 → QA 팝업 닫기 → 파일 첨부 → confirm 다이얼로그 자동 승인 →
서버 커밋 완료까지 대기하는 전체 흐름을 통합 테스트로 다시 돌려 정상 동작(성공 판정 +
스크린샷 3장 모두 캡처)함을 확인했습니다.

🆕 기능 추가 (2026-08-27) — "버튼 클릭이 실제로 서버에 전달됐는지"를 추측이 아니라
증거로 자동 판정하는 진단 기능
대기 시간을 늘리고 클릭 타이밍까지 고쳤는데도 같은 문제가 반복된다는 피드백을 받고,
더 이상 추측으로 고치지 않고 실제로 클릭했을 때 무슨 일이 일어나는지 직접 관찰할 수
있도록 계측을 추가했습니다. 이제 페이지의 콘솔 로그(자바스크립트 오류 포함)와 네트워크
요청/응답을 전부 기록하면서 업로드 버튼을 "클릭하는 순간"을 기준으로 그 전/후를
구분합니다. 계정별 결과에 "진단" 정보가 자동으로 추가되어 (1) 클릭 후 서버로 요청이

닫아버려서 업로드가 진행되지 않는 것처럼 보인다고 하셨습니다. 이 두 가지를 같이
놓고 다시 코드를 점검한 결과, 실제로 방치돼 있던 구조적인 버그를 찾았습니다.

지금까지 확인창 문제에 쓴 수정(window.confirm/alert 오버라이드, context.on
("dialog"))은 전부 "네이티브 자바스크립트 대화상자"(confirm()/alert())에만
적용되는 방식이었습니다. 그런데 카페24의 이 확인창이 네이티브 대화상자가 아니라
window.open()으로 열리는 진짜 별도의 팝업 페이지(새 탭/창)에 HTML로 그려지는
"확인" 버튼일 가능성이 있다는 것을 이번에 다시 점검하면서 발견했습니다. 이 경우
window.confirm 오버라이드는 애초에 confirm()을 호출하는 게 아니므로 전혀 관여하지
못합니다. 게다가 기존 코드의 "_close_popups"(팝업 정리 함수) 안에는 메인 페이지가
아닌 다른 모든 페이지를, 그 안의 내용이 무엇인지 전혀 확인하지 않고 무조건 닫아
버리는 코드가 그대로 남아 있었습니다 — 만약 이 확인창이 그런 팝업 페이지였다면,
"확인" 버튼을 눌러볼 기회도 없이 그냥 닫혀버렸을 것이고, 이는 사용자가 화면에서
직접 목격한 증상과 정확히 일치합니다.

이번 수정으로:
1) 새로운 팝업 페이지가 열리는 즉시(페이지 생성 이벤트) 그 안에서 "확인"류 버튼을
   자동으로 찾아 클릭하는 안전장치를 추가했습니다. 네이티브 대화상자와 달리 실제
   페이지에 그려지는 버튼은 Playwright가 자동으로 취소해버리지 않고 그대로
   남아있으므로, 늦게 반응해도 놓치는 경쟁 상태가 없습니다.
2) 팝업 정리 함수(_close_popups)도 다른 페이지를 무조건 닫기 전에, 먼저 그 안에서
   "확인" 버튼을 찾아 클릭을 시도하도록 고쳤습니다. 확인 버튼을 찾아 눌렀다면 그
   페이지를 곧바로 닫지 않습니다(그 클릭으로 나간 실제 업로드 요청이 중간에
   끊어지지 않도록 하기 위함). "확인" 버튼을 끝내 찾지 못한 경우(=업로드 확인창이
   아니라 진짜 광고/안내성 팝업으로 판단)에만 기존처럼 정리하고 닫습니다.
3) "요청은 나갔는데 응답이 없다"는 진단이, 실제로는 서로 다른 두 가지 상황(서버가
   느린 것 / 요청 자체가 중간에 끊어진 것)을 구분하지 못하고 있었습니다. 이제는
   Playwright의 requestfailed 이벤트를 함께 기록해서, 요청이 진짜로 중단된 경우에는
   "대기 시간을 늘려도 해결되지 않습니다"라고 더 정확하게 안내합니다.
4) 새로 열린 팝업 페이지마다 어떤 조치를 했는지("확인 버튼 자동 클릭" 또는 "확인
   버튼을 찾지 못해 닫음")를 시간 순서대로 기록하는 "팝업 페이지 처리 로그"를
   추가하고, 화면의 "④ 업로드 결과 → 상세 로그"에서 확인할 수 있게 했습니다. 문제가
   다시 재현되면 이 로그를 함께 보내주시면 정확한 원인 파악에 큰 도움이 됩니다.

로컬 테스트로, 확인창이 네이티브 대화상자가 아니라 진짜 팝업 페이지의 DOM "확인"
버튼으로 뜨는 상황을 새로 재현해서: 수정 전에는(이 새 페이지 이벤트 핸들러가 없던
상태) 그 버튼을 눌러볼 방법이 없어 업로드 요청 자체가 나가지 않았던 것을, 수정
후에는 새로 열린 팝업 페이지 안의 "확인" 버튼이 자동으로 클릭되고 실제 업로드
요청까지 정상 응답을 받는 것을 확인했습니다. 또한 요청이 중간에 끊어지는 상황도
별도로 재현해서, "서버가 느림"이 아니라 "요청이 중단됨"으로 더 정확하게 진단되는
것도 확인했습니다. 기존 5가지 정상/오류/팝업 시나리오도 모두 다시 돌려 회귀가 없음을
재검증했고, Streamlit 앱 부팅 테스트도 재검증했습니다.
※ 이번 수정은 "확인창이 네이티브 대화상자가 아니라 진짜 팝업 페이지였을 것"이라는
추론에 기반한 것이라, 실제 계정에서 재현되지 않는다는 것을 이번에도 최종적으로
확인해주셔야 합니다. 이번에도 문제가 재현되면, 화면 위쪽의 "코드 버전" 표시와

저희 코드를 다시 보니, 파일을 화면에 첨부한(input에 지정한) 직후 바로 임시 파일을

미리 읽어서 담아두는 게 아니라, "이 경로의 파일을 나중에 실제 제출할 때 읽어라"는
식으로 경로만 기억해둡니다. 그래서 파일을 첨부한 직후 곧바로 지워버리면, 몇 초 뒤
실제로 업로드 버튼을 눌러 폼이 제출되는 순간에는 이미 파일이 없어서 이 오류가 나는
것이었습니다.

사용자께서 예전에 로컬에서 매크로(Selenium + pywinmacro)로 쓰시던 코드를 보내주셔서

확인창 관련 수정을 반복해도 계속 재현됐던 문제의 진짜 원인이었습니다 — 확인창 자체는
이미 정상적으로 처리되고 있었는데, 그 다음 단계에서 파일이 사라져서 업로드 요청이
