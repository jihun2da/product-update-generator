신상품 업데이트 파일 생성기 (로컬 웹앱)
========================================

실행 방법
---------
1) 파이썬이 설치되어 있어야 합니다 (기존에 옵션ver3.py / 자동업데이트파일생성(2026).py를
   실행하시던 환경이면 그대로 사용 가능합니다).
2) 이 폴더에서 아래 명령으로 필요한 패키지를 설치합니다.
       pip install -r requirements.txt
3) 아래 명령으로 앱을 실행합니다.
       streamlit run app.py
4) 자동으로 브라우저가 열립니다(안 열리면 터미널에 나오는 http://localhost:8501 주소로 접속).

사용 방법
---------
왼쪽 사이드바에서
  - 기린.xlsx, S파일(예: S20260820.xlsx) 두 개를 업로드 (필수)
  - 카테고리번호.xlsx는 업로드하지 않으면 앱에 저장된 기본 파일을 사용합니다.
  - 스마트스토어기본.xlsx(템플릿)를 업로드하면 N파일(스마트스토어 변환)까지 생성됩니다.
    업로드하지 않으면 이 단계만 건너뛰고 나머지는 정상적으로 생성됩니다.
  - 카테고리번호.xlsx / 스마트스토어기본.xlsx를 업로드했을 때, 그 옆의
    "앱의 새 기본값으로 영구 저장(교체)" 체크박스를 켜고 실행하면, 업로드한 파일이
    깃허브 저장소의 기본 파일 자체를 교체합니다. 그러면 이후에는 매번 업로드하지 않아도
    이 파일이 새 기본값으로 자동 사용됩니다(카테고리가 새로 추가되는 등 파일 내용이
    바뀌었을 때만 체크해서 사용하고, 평소에는 체크하지 않은 채 그냥 실행하면 됩니다).
    이 기능을 쓰려면 아래 "기본값 영구 저장 기능 설정" 부분을 먼저 한 번 설정해야 합니다.
  - 날짜/카테고리 행 번호 등은 필요하면 조정하세요.
'전체 파이프라인 실행' 버튼을 누르면 아래 순서로 처리됩니다.

  0단계 (수작업이었던 부분 자동화)
    기린.xlsx의 E,F,G열 -> S파일의 E,F,G열로 복사
    이 시점 상태를 곽충현.xlsx(스냅샷) / 문정희.xlsx로 저장
      - 곽충현.xlsx는 현재 "이름만 바꿔서 저장"하는 자리표시 단계입니다(전용 가공 규칙 추가 예정).
      - 문정희.xlsx는 2단계 문정희 로직과 동일한 규칙("<" 이후 삭제 + "KC" 제거 + 상품명 앞
        "[상시의류]" 접두어)을 이 시점에 바로 적용해 최종본으로 만듭니다. 2단계에서는 더 이상
        문정희 파일을 따로 만들지 않습니다(중복 방지).
      - 곽충현.xlsx / 문정희.xlsx 모두, 카테고리번호.xlsx에 '곽충현' / '문정희' 이름의 컬럼이
        있으면 2단계 판매처 파일들과 동일한 방식으로 E열(상품분류 번호)을 그 컬럼 값으로
        매핑해서 생성합니다(원본 코드 -> 해당 판매처 전용 코드). 해당 컬럼이 없으면 매핑 없이
        원본 코드 그대로 두고 로그에 안내를 남깁니다.
    기린.xlsx의 AJ열 -> S파일의 AJ열로 복사 → 이 상태 = 예제.xlsx

  1단계 (기존 옵션ver3.py 로직)
    예제.xlsx -> 사이즈별 추가금 그룹 분리 + 가격 재계산 -> 새 기린.xlsx
    새 기린.xlsx -> 색상별 행 분리 + 상품명 정리 -> 날짜파일(예: 20260819.xlsx)
    새 기린.xlsx 그대로 -> 두두사사.xlsx 로 저장
    새 기린.xlsx의 E,F,G를 지운 사본 -> 다음 라운드용 S파일(예: S20260820.xlsx)
    새 기린.xlsx E열의 마지막 '|' 값(예: 6136) -> 카테고리번호.xlsx 29행 A열에 반영

  2단계 (기존 자동업데이트파일생성(2026).py 로직)
    두두사사.xlsx -> 김하늘/서송이/이지민/해피/김다혜/박미리/오토/오마베/최민기/
    현건주/목윤희/최은경/남부센/백종열/X날짜/백성희/모나마켓/이모이모
    (총 18개, 문정희 제외 — 0단계에서 이미 생성) 판매처별 파일 생성
      - 김하늘.xlsx: 소비자가(T열)/판매가(V열)을 공급가(U열) * 1.7 값으로 생성
      - 서송이.xlsx: 적립금(AB열) 값을 모두 비워서 생성(생성 직후 0이 아니라 빈 값)
      - 모나마켓.xlsx: 진열상태(C열)/판매상태(D열)을 Y가 아닌 N으로 생성
    + (템플릿 있으면) 스마트스토어 N파일 생성
      - 데이터가 500행을 넘으면 500행 단위로 잘라 N{날짜}-1.xlsx, N{날짜}-2.xlsx ...
        형태로 여러 파일로 나눠 생성합니다(500행 이하면 N{날짜}.xlsx 한 개).
    -> 카테고리번호.xlsx로 각 파일 E/F/G, N파일(들) B열 매핑
    -> 오토.xlsx 상품명 뒤에 매핑값 추가 (N파일이 여러 개로 나뉜 경우 순서대로 이어붙여 매핑)
    -> 금/오토/0/X날짜 파일 E,F,G 초기화

결과는 '1단계_예제생성' 폴더와 '2단계_판매처파일' 폴더로 나뉜 ZIP 파일로 한 번에
다운로드하거나, 개별 파일 버튼으로 하나씩 받을 수 있습니다.

기본값 영구 저장 기능 설정 (카테고리번호/스마트스토어기본 교체용, 최초 1회만)
----------------------------------------------------------------
"앱의 새 기본값으로 영구 저장(교체)" 체크박스를 쓰려면, 깃허브 저장소에 대신 커밋해 줄
권한이 있는 GitHub Personal Access Token을 앱에 등록해야 합니다. (이 토큰은 저(Claude)에게
알려주실 필요가 없습니다 — 아래처럼 본인이 직접 Streamlit Cloud 설정 화면에만 입력하시면 됩니다.)

1) GitHub 접속 -> 오른쪽 위 프로필 -> Settings -> 왼쪽 메뉴 맨 아래 "Developer settings"
   -> "Personal access tokens" -> "Fine-grained tokens" -> "Generate new token"
2) Repository access를 "Only select repositories"로 두고 product-update-generator 저장소 선택
3) Permissions -> Repository permissions -> "Contents"를 "Read and write"로 설정 -> 토큰 생성
4) 생성된 토큰(ghp_로 시작하는 문자열)을 복사
5) https://share.streamlit.io 접속 -> 이 앱(kirin-newitem-update) -> 오른쪽 "⋮" 메뉴(또는
   Manage app) -> "Settings" -> "Secrets" 탭 -> 아래 내용 입력 후 저장
       GITHUB_TOKEN = "여기에_복사한_토큰_붙여넣기"
6) 저장하면 앱이 자동으로 재시작됩니다. 이후부터 체크박스 기능을 사용할 수 있습니다.

이 설정을 아직 하지 않았다면, 체크박스를 켜고 실행해도 "GITHUB_TOKEN이 설정되어 있지
않아..." 라는 안내만 나오고 파이프라인 실행 자체는 정상적으로 계속 진행됩니다(저장만
실패할 뿐, 나머지 파일 생성에는 영향이 없습니다).

카페24 자동 업로드 (베타, 별도 탭)
----------------------------------
왼쪽 사이드바 위쪽에 "1 카페24 업로드" 라는 별도 페이지(탭)가 추가됩니다. 기존
"신상품 업데이트 파일 생성기"(이 페이지) 와는 완전히 분리된 기능이라, 이 기능에 문제가
생겨도 기존 파일 생성 기능에는 영향을 주지 않습니다.

무엇을 하는 기능인가요?
  2단계에서 생성된 판매처별 파일들을 카페24 관리자(eclogin.cafe24.com)에 계정별로
  자동 로그인해서, 상품 엑셀 일괄등록/수정 화면에 자동으로 업로드해줍니다.

사용 준비 (최초 1회, "카페24 업로드" 페이지에서 진행)
  1) 이름/아이디/비밀번호 컬럼이 있는 엑셀(예: 아이디비번.xlsx)을 "① Secrets 등록 도우미"에
     올리면, Secrets에 붙여넣을 텍스트 파일(cafe24_secrets.toml)을 만들어 다운로드해줍니다
     (화면에는 마스킹된 값만 보이고, 실제 아이디/비밀번호는 파일로만 전달됩니다).
     - 서로 다른 아이디인데 같은 파일을 올려야 하는 계정이 여러 개라면, '이름' 컬럼에
       같은 이름을 그대로 여러 번 써서 올려도 됩니다. 예전에는 이런 경우를 실수로 생긴
       중복으로 보고 마지막 행 것만 남기고 지웠는데, 지금은 전부 별도 계정으로 등록하고
       (Secrets 키만 "이름", "이름_2", "이름_3"... 로 자동 구분) 실제 업로드할 파일과
       매칭할 때 쓰는 이름은 원래 이름 그대로 유지합니다. 그래서 같은 이름을 쓴 계정들은
       모두 같은 파일과 자동으로 매칭됩니다. 필요하면 '파일명' 컬럼을 추가로 넣어서,
       업로드할 파일 이름을 '이름'과 다르게 직접 지정할 수도 있습니다(선택 사항).
  2) https://share.streamlit.io 접속 -> 이 앱 관리 화면 -> Settings -> Secrets 탭에서
     기존 내용 아래에 다운로드한 파일 내용을 그대로 붙여넣고 저장합니다.
  3) 저장하면 앱이 재시작되고, "카페24 업로드" 페이지의 "②" 목록에 등록된 계정이
     나타납니다.

사용 방법
  1) "②" 에서 업로드할 판매처 파일들을 올립니다. 파일명이 Secrets에 등록한 계정의
     매칭용 파일명(기본값 = 계정 이름)과 정확히 같아야 자동으로 매칭됩니다
     (예: 김하늘.xlsx -> "김하늘" 계정으로 업로드). 일치하지 않는 파일은 업로드
     대상에서 제외되고 화면에 안내됩니다.
     - 아이디는 다른데 같은 파일을 올려야 하는 계정이 여러 개 등록돼 있으면(위 '①'
       참고), 파일 1개를 올렸을 때 그 계정 전부가 한꺼번에 매칭되어, 같은 파일이
       각 계정에 순서대로 업로드됩니다.
     - 파일명이 "X20260820.xlsx"처럼 뒤에 8자리 날짜가 붙어서 매일 바뀌는 경우에는,
       Secrets에 계정의 매칭용 파일명을 날짜 없이 "X"로만 등록해두면 됩니다. 파일명
       뒤의 날짜가 무엇이든(20260820, 20260821, ...) 날짜를 뗀 나머지("X")가 매칭용
       파일명과 같으면 자동으로 매칭되고, 화면에 "날짜 패턴으로 매칭된 파일"로
       안내됩니다. 서로 다른 매칭용 파일명이 날짜를 떼면 똑같아지는 경우(예:
       "X20260101"과 "X"가 둘 다 등록된 경우)는 어느 쪽인지 특정할 수 없으므로
       매칭하지 않고 경고로 알려줍니다 — 이런 경우 "X"처럼 날짜 없는 형태 하나로
       통일해서 등록해주세요.
       같은 계정에 파일이 2개 이상 매칭되면(예: X파일을 실수로 여러 날짜치 같이 올린
       경우) 같은 계정으로 중복 업로드가 되니 미리 경고로 알려줍니다.
  2) "③ 업로드 실행"에서 "선택된 계정 업로드 시작"을 누르면 계정을 순서대로 처리합니다.
     실패한 계정은 재시도하지 않고, 끝까지 진행한 뒤 실패한 계정 이름을 모아서 알려줍니다.
  3) "④ 업로드 결과"에서 계정별 성공/실패 여부와 스크린샷을 확인할 수 있습니다.

✅ 실제 계정으로 전체 흐름(로그인 → 업로드 화면 이동 → 파일 업로드 → 성공/실패 판별)을
직접 테스트해서 정상 동작하는 것을 확인했습니다(2026-08-26). 계정별 스크린샷은 "④
업로드 결과"에서 계속 확인할 수 있으니, 새로운 계정이나 파일을 처음 추가할 때는 결과를
한 번씩 확인해보시는 걸 권장드립니다. 판별 문구가 이후에 달라지는 경우가 생기면
알려주시면 바로 수정하겠습니다.

⚠️ 오류 수정 (2026-08-26) — "성공으로 나왔는데 실제로는 아무것도 업로드되지 않음"
문제: 업로드 화면에서 "전용 엑셀양식 다운로드" 같은 안내 팝업이 새로 뜨면서 업로드
버튼을 가려, 실제로는 버튼 클릭 자체가 막혔는데도 이를 조용히 넘어가서 "성공"으로
잘못 표시되는 문제가 있었습니다. 이제는:
  - 업로드 화면 진입 직후, 파일 첨부 후 등 여러 시점에서 팝업을 자동으로 정리하도록
    강화했고,
  - 그래도 업로드 버튼 클릭이 끝내 막히면(팝업이 안 닫히는 경우 등) 더 이상 "성공"으로
    처리하지 않고, 화면에 남아있던 팝업 내용을 메시지에 담아 "오류"로 명확히
    보고합니다.
로컬 테스트 페이지로 "팝업이 버튼을 가리는 상황 → 자동으로 닫고 재시도 → 성공",
"팝업이 안 닫히는 상황 → 오류로 보고(성공으로 잘못 표시 안 됨)", "팝업이 아예 없는
정상 상황 → 그대로 성공" 세 가지 시나리오를 재현해서 검증했습니다. 다만 클라우드
환경은 headless(화면 없이) 실행이라 진행 과정을 직접 눈으로 볼 수는 없고, 계정별
스크린샷으로만 확인할 수 있습니다 — 실행 과정을 직접 눈으로 보고 싶으시면, 이 앱을
본인 컴퓨터에 내려받아 `streamlit run app.py`로 로컬 실행한 뒤 "③"의 headless 체크를
해제하고 실행하시면 브라우저 창이 실제로 뜨는 걸 볼 수 있습니다(Streamlit Cloud에는
화면이 없어서 이 옵션이 동작하지 않습니다).

⚠️ 오류 수정 (2026-08-26) — 로컬(Windows)에서 실행 시 "NotImplementedError" 발생

  1) 진단 로직이 "클릭 후 오류 응답이 없었다"는 것만 확인하고, 실제 업로드 처리를
     담당하는 서버 요청(`.../exec/admin/product/ProductExcelSet`, 실제 계정 테스트로
     확인된 진짜 업로드 제출 주소)이 응답을 "받았는지"는 확인하지 않고 있었습니다.
     요청은 보냈지만 응답을 못 받은 경우(서버 처리가 오래 걸리는데 앱이 먼저 포기한
     경우 등)도 "오류 응답이 없다"는 이유만으로 🟢(정상)로 잘못 표시됐습니다.
  2) 더 근본적으로, 이 응답을 기다리는 대기 루프가 순수 파이썬 time.sleep()을
     사용하고 있었는데, Playwright의 동기(sync) API는 등록해둔 이벤트 콜백
     (page.on("response") 등)을 "메인 스레드가 Playwright API를 실제로 호출할 때"
     함께 처리(pump)하는 구조라서, time.sleep()으로만 기다리면 그 사이에 실제로
     도착한 서버 응답 이벤트가 큐에 쌓인 채 전달되지 않는 경우가 있었습니다. 로컬
     테스트로 이 현상을 직접 재현했습니다 — 응답이 실제로는 1.5초 만에 도착했는데도
     time.sleep() 기반 대기 루프는 10초 내내 "응답 없음"으로 보고, 그 뒤 다른
     Playwright 호출로 넘어가고 나서야 뒤늦게 응답이 잡히는 것을 확인했습니다.
수정 내용:
  - 이제 "엑셀 업로드" 버튼이 실제로 호출하는 서버 요청(ProductExcelSet)만 구체적으로
    추적해서, 그 요청이 (a) 아예 발생하지 않았는지, (b) 요청은 갔는데 응답을 못
    받았는지, (c) 응답은 받았는데 오류(4xx/5xx)였는지, (d) 정상 응답(200)까지
    받았는지를 구분해서 진단합니다. (d)인 경우만 🟢이고, 나머지는 모두 🟠/🔴로
    표시됩니다.
  - 상태 판정도 함께 바꿨습니다: 예전에는 화면 문구에 명시적인 실패 단어가 없으면
    무조건 "성공"으로 표시했는데, 이제는 진단이 확실히 🟢(정상 응답까지 확인)인
    경우에만 "성공"으로 표시하고, 그 외(🔴/🟠/🟡, 즉 확실한 성공 증거가 없는 모든
    경우)는 "오류"로 표시해서 "④ 업로드 결과"의 실패 안내와 진단 패널을 반드시
    확인하도록 만들었습니다.
  - 응답을 기다리는 대기 루프(및 클릭 직전 타이밍 대기)를 모두 time.sleep() 대신
    page.wait_for_timeout()으로 바꿔서, 대기 중에도 Playwright 이벤트가 제때
    처리되도록 수정했습니다.
  - "③ 업로드 실행"에 "업로드 처리 완료(서버 응답)까지 최대 대기 시간(초)" 옵션을
    새로 추가했습니다(기본값 180초). 상품 수가 아주 많아 서버 처리가 오래 걸리는
    계정이 있으면 이 값을 늘리면 됩니다. 기존 "클릭 후 최종 대기 시간" 옵션은 이
    응답 대기가 끝난 뒤 추가로 더 기다리는 시간으로 그대로 유지됩니다.
로컬 테스트 서버 4가지 시나리오로 검증했습니다: (1) 정상 흐름(요청+정상 응답) → 🟢
+ 성공, (2) 눈속임 버튼(요청 자체가 안 감) → 🔴 + 오류, (3) 응답이 느리게 오는데
대기 시간을 짧게 주면 → 🔴 + 오류(타임아웃, 지금까지 겪은 문제를 그대로 재현), (4)
같은 상황에서 대기 시간을 충분히 늘리면 → 🟢 + 성공(해결 확인). 4가지 모두 기대한
대로 통과했고, Streamlit 앱 부팅 테스트(app.py / 카페24 업로드 페이지)와 실제
업로드 결과 화면 렌더링(가짜 결과 데이터 주입)도 함께 재검증해 회귀가 없음을
확인했습니다.
※ 이 수정이 실제 계정에서도 최종 해결인지는 아직 100% 확정할 수 없습니다 — 로컬
재현 테스트로는 확실히 원인과 해결을 증명했지만, 다음 실제 테스트에서 "④ 업로드
결과 → 🔍 진단 정보"를 함께 확인해주시면 더 확실히 알 수 있습니다. 이번에도 문제가
남아있다면, 이제는 진단 정보에 "요청은 갔는데 응답을 못 받음(대기 시간 부족)"인지
"요청 자체가 안 감"인지가 명확히 구분되어 나오므로, 그 내용을 그대로 알려주시면
훨씬 빠르게 원인을 좁힐 수 있습니다.

⚠️ 오류 수정 (2026-08-27) — "해당 파일을 업로드 하시겠습니까?" 확인창이 뜨면 계속
자동으로 취소되던 진짜 원인 (팝업 페이지에서 뜨는 확인창을 놓치던 문제)
사용자가 실제 화면에서 이 확인창이 뜬 스크린샷을 캡처해서 보내주셨는데, "확인"을
눌러야 업로드가 진행되는데도 계속 그냥 닫히기만(취소) 한다는 문제였습니다. 이전
수정(위 2026-08-27자 "네이티브 확인창을 자동 승인" 항목)에서 확인창 자동 승인
기능을 추가했는데도 왜 안 되는지, 로컬 테스트로 직접 원인을 재현해서 찾았습니다.
카페24 관리자 화면은 실제로 새 탭/팝업 페이지가 뜨는 경우가 있는데(_close_popups()가
"다른 페이지"를 닫는 로직이 있는 것도 이 때문입니다), 문제의 확인창이 원래 페이지가
아니라 이런 새 팝업 페이지 쪽에서 뜨는 경우, "원래 페이지 객체" 하나에만 등록해둔
확인창 자동 승인 핸들러는 그 확인창을 전혀 못 잡습니다. Playwright는 확인창을 처리할
리스너가 없는 페이지에서 뜨는 확인창을 기본적으로 즉시 자동 "취소" 처리하는데, 이게
정확히 겪고 계신 증상(확인창이 뜨자마자 그냥 닫힘)과 일치한다는 것을 로컬 재현
테스트로 직접 확인했습니다. 처음에는 새로 생기는 페이지마다 개별적으로 리스너를
붙이는 방식을 시도했는데, 팝업이 뜨자마자(페이지가 열리는 도중 곧바로) 확인창을
띄우는 경우에는 그 등록 자체가 확인창이 뜨는 시점을 놓치는 경쟁 상태(race condition)
가 실제로 재현됐습니다. 대신 브라우저 컨텍스트 자체에 확인창 핸들러를 등록하는
방식(Playwright 최신 버전에서 지원)으로 바꿔서, 원래 페이지든 이후에 새로 뜨는 어떤
팝업 페이지든 상관없이 확인창을 놓치지 않고 항상 자동으로 "확인" 처리하도록
수정했습니다. 같은 이유로, 콘솔 로그·네트워크 요청/응답을 기록하는 진단 계측도
원래 페이지 하나에만 등록돼 있으면 실제 업로드 요청이 팝업 페이지 쪽에서 발생할 때
완전히 놓치는 것이 확인돼서(확인창은 정상적으로 승인됐는데도 진단은 "요청이 전혀
없었다"로 잘못 나오는 것을 직접 확인), 이것도 함께 컨텍스트 레벨로 옮겼습니다.
로컬 테스트로, 확인창이 팝업 페이지에서 뜨고 실제 업로드 요청도 그 팝업 페이지에서
발생하는 상황을 재현해서: 수정 전에는 확인창이 자동으로 취소되고 업로드 요청 자체가
전혀 안 나가는 것(오류로 정확히 판정)을, 수정 후에는 확인창이 정상적으로 자동 승인
되고 실제 업로드 요청까지 정상 응답을 받는 것(성공으로 정확히 판정)을 확인했습니다.
기존 4가지 정상/오류 시나리오도 모두 다시 돌려 회귀가 없음을 확인했고, Streamlit
앱 부팅 테스트도 재검증했습니다.

환경과는 다른 타이밍 경쟁에 걸릴 가능성을 배제할 수 없었습니다(이 작업 환경에는

잡아서 처리하는 대신, 페이지의 다른 스크립트가 실행되기도 전에 window.confirm()

시점이나 처리 순서와 완전히 무관합니다 —애초에 진짜 확인창이 생기지 않으므로
"늦게 잡아서 취소되는" 종류의 문제 자체가 원천적으로 불가능합니다. headless든
아니든, 메인 페이지든 새로 뜨는 팝업 페이지든 모두 동일하게 적용됩니다. 기존
context.on("dialog") 핸들러도 다른 종류의 예외적인 다이얼로그에 대비해 이중
안전장치로 그대로 남겨뒀습니다. 로컬 테스트로 (1) 메인 페이지의 confirm(), (2) 팝업
페이지에서 페이지 로드와 거의 동시에 뜨는 confirm() 두 경우 모두 자동으로 즉시

재검증했습니다.
